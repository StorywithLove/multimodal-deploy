## 坑一：`No module named 'diffusers'`

错误发生在 `from diffusers import Flux2KleinPipeline`，模型还未加载。GPU 32GB / 64GB、优惠券 / 自费不会直接决定 Python 能否找到包；PyTorch 版本一致也不代表全部依赖一致。

教程的沐曦章节仅指定 C500（64GB）、`pytorch>=2.4`，随后直接导入 Diffusers，未列安装命令和 Diffusers 版本；不能假设镜像已经预装。昇腾章节列了安装步骤，但不是沐曦章节的明确前置任务。

在当前 Notebook 检查并补装：

```python

```

```python

```

安装后重启内核，再验证管道类导入。`%pip` 针对当前内核，避免终端 pip 与 Notebook Python 不一致。Accelerate 和 Diffusers 是不同包，安装前者不能替代后者。保留沐曦适配版 torch，不为修复上层依赖而盲目升级核心环境。

当前 Diffusers 的 `torch_dtype` 弃用提醒可通过改成 `dtype=` 消除；FutureWarning 本身不是此次失败原因。

```text
→ self.keys = torch.cat([self.keys, key_states], dim=-2)

```

单次提示词编码不需要依赖逐 token 续写缓存。用户确认，设置下面这一行后生成成功：

```python
pipe.text_encoder.config.use_cache = False
```

这证明绕过缓存更新可解决该环境下的当前故障，但没有查明具体库版本或厂商适配根因。不能推出“沐曦不支持 KV Cache”；vLLM 的缓存实现与此不同。

### 整理后的运行代码

切换模型前重启内核，避免旧模型继续占显存。以下使用本轮已经跑通的管道、dtype 与缓存设置：

```python
from pathlib import Path
import torch
from diffusers import ZImagePipeline

pipe = ZImagePipeline.from_pretrained(
    "/mnt/moark-models/Z-Image-Turbo",
    dtype=torch.bfloat16,
    local_files_only=True,
)
pipe = pipe.to("cuda")
pipe.text_encoder.config.use_cache = False

prompt = "一只可爱的橘色小猫坐在窗台上，窗外是夕阳余晖洒满的城市天际线，温暖的光线照在猫咪毛发上。高清摄影风格，细节丰富。"
with torch.inference_mode():
    image = pipe(
        prompt=prompt,
        width=512,
        height=512,
        guidance_scale=0.0,
        num_inference_steps=9,
        generator=torch.Generator(device="cuda").manual_seed(42),
    ).images[0]

output = Path("/data/exam/image_output.png")
output.parent.mkdir(parents=True, exist_ok=True)
image.save(output)
image.save("z_image_test.png")
print(output)
```

## Qwen-Image-2512 成功路线

### 坑五：顶层与嵌套配置都关闭缓存，仍然报错

Qwen-Image 的文本编码器是 Qwen2.5-VL，内部有语言模型。先后尝试顶层 `config.use_cache=False` 和遍历子模块修改 `text_config.use_cache`，均未阻止实际调用进入 `past_key_values.update()`。

最终有效方法：给外层文本编码器和内部 `Qwen2_5_VLTextModel` 注册 forward pre-hook，在调用时显式传 `use_cache=False`、`past_key_values=None`。单独编码测试返回 `torch.Size([1, 12, 3584])`，用户确认通过。

钩子是当前版本环境的临时绕过，不是通用必需设置；不修改磁盘上的库代码，内核重启后失效，需要重新注册。对话没有确认为何配置默认值未生效，不将猜测记为根因。

### 坑六：CPU 分层卸载反而触发系统 OOM

早先按 32GB 显存假设使用 `enable_sequential_cpu_offload()`，保留大量 CPU 权重。文本编码通过后，生图阶段内核直接退出，50 步和 2 步都崩溃，进度停在 0%。降低步数降低总计算量，不会按比例降低第一次迭代的内存峰值。

实际检查得到：

```text
free -h：48Gi 总内存，重启后可用约 43Gi；Swap 0
memory.max：51539607552
memory.events：max 1251631 / oom 3 / oom_kill 3
mx-smi：MetaX C500，显存 65536 MiB
```

`oom_kill=3` 是容器累计系统内存杀进程证据，不能独立逐次对应每次崩溃；结合反复退出与改方案成功，系统内存压力是最有力解释。重启后看到空闲内存，不代表运行峰值没有超限。`dmesg` 无权限不等于没有 OOM。

修正：当前实际是 64GB GPU，移除 CPU 分层卸载，加载时使用 `device_map="cuda"` 和 `low_cpu_mem_usage=True`。用户随后确认生成成功。避免“先完整加载到 CPU，再 `.to('cuda')`”带来的系统内存压力，也不同时启用 CPU offload。

### 最终组合代码

以下组合了用户确认有效的 GPU 加载方式、缓存钩子及生成步骤；是对成功过程的整理，不声称该合并代码又独立执行了一轮。

```python
from pathlib import Path
import torch
from diffusers import QwenImagePipeline

pipe = QwenImagePipeline.from_pretrained(
    "/mnt/moark-models/Qwen-Image-2512",
    dtype=torch.bfloat16,
    local_files_only=True,
    low_cpu_mem_usage=True,
    device_map="cuda",
)

def disable_kv_cache(module, args, kwargs):
    kwargs["use_cache"] = False
    kwargs["past_key_values"] = None
    return args, kwargs

targets = [pipe.text_encoder]
targets.extend(
    module for module in pipe.text_encoder.modules()
    if type(module).__name__ == "Qwen2_5_VLTextModel"
)
pipe._no_kv_cache_handles = [
    module.register_forward_pre_hook(disable_kv_cache, with_kwargs=True)
    for module in targets
]
pipe.vae.enable_tiling()

prompt = "一只可爱的橘色小猫坐在窗台上，窗外是夕阳余晖洒满的城市天际线，温暖的光线照在猫咪毛发上。高清摄影风格，细节丰富。"
negative_prompt = "低画质，模糊，畸形，多余肢体，过度饱和"

with torch.inference_mode():
    image = pipe(
        prompt=prompt,
        negative_prompt=negative_prompt,
        width=512,
        height=512,
        num_inference_steps=50,
        true_cfg_scale=4.0,
        generator=torch.Generator(device="cuda").manual_seed(42),
    ).images[0]

output = Path("/data/exam/image_output.png")
output.parent.mkdir(parents=True, exist_ok=True)
image.save(output)
image.save("qwen_image_test.png")
print(output)
```

不要对同一个 `pipe` 重复注册钩子；如果需要重设，先对 `pipe._no_kv_cache_handles` 调用 `handle.remove()`。内核重启后，导入、模型、钩子和 Python 变量都需重建，但已安装包及磁盘文件通常不因内核重启而丢失。

## 坑七：图片已生成，保存却失败

```text
FileNotFoundError: /data/exam/image_output.png
```

PIL 可以创建目标文件，不会创建父目录。执行 `Path('/data/exam').mkdir(parents=True, exist_ok=True)` 后再保存。若内核仍在，直接使用已有 `image`，不用重跑生成。

连续两次 `image.save()` 可将同一张图片保存到两个位置；绝对路径写到指定目录，相对路径写到当前工作目录。第一次保存抛错时，第二次尚未执行。同名文件会覆盖；对比两个模型时分别保留 `z_image_test.png`、`qwen_image_test.png`，避免只剩最后一张。

## API 任务：方案已给出，尚待云端验收

任务要求 FastAPI + Pydantic，端口 8188，`POST /v1/images/generations` 接收 JSON，返回 `data[].b64_json`。对话提供的方案要点：

- 使用 FastAPI `lifespan` 在启动时加载一次管道，沿用上面的 GPU 分配和缓存钩子。
- 启动前重启 Notebook 内核释放旧模型；停止旧 vLLM 服务，避免端口、显存冲突。
- `uvicorn` 使用单 worker，不启用 reload，避免重复加载。
- 同一管道用锁串行处理请求；`n>1` 逐张生成，种子按 `seed+i`。
- 请求字段 `guidance_scale` 映射为 Qwen 的 `true_cfg_scale`，提供 `negative_prompt=""` 使 CFG 路径有负面输入；它不是 Z-Image 的同义采样配置。
- 使用 `io.BytesIO()` 将 PIL 图像保存成 PNG，再 `base64.b64encode(...).decode('ascii')`，响应由 Pydantic 模型定义。
- 校验 `model`、尺寸、步数和 n；尺寸范围只是输入限制，不是显存足够保证。

启动形式（`image_api.py` 是对话中的建议文件名，当前仓库未提供或运行该服务文件）：

```bash
cd /data/exam
python -m uvicorn image_api:app --host 0.0.0.0 --port 8188 --workers 1
```

验收请求，需在云端服务器另一个终端执行：

```bash
curl --fail-with-body http://127.0.0.1:8188/v1/images/generations \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "Qwen-Image-2512",
    "prompt": "一只可爱的橘色小猫坐在窗台上，夕阳余晖，高清摄影风格。",
    "size": "1024x1024",
    "num_inference_steps": 30,
    "guidance_scale": 7.5,
    "seed": 42,
    "n": 1
  }' \
  -o /data/exam/api_response.json
```

预期响应 `{"data":[{"b64_json":"..."}]}`，可额外包含 `created`。还需 base64 解码、PIL 打开并检查图像尺寸，才算端到端通过。不能因为单次 Notebook 生图成功，就记为 API 已验收；该格式是任务指定的 OpenAI 风格子集，不是全部 Images API 功能。
